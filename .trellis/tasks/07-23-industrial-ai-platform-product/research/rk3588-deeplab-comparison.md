## 关键实现细节

### 1. RK 项目为什么把 resize 移到模型外

RK 项目在普通 DeepLabV3+ 变体中将 `upsampling=1`，训练时再把 deployment logits 插值到标签尺寸；注释明确说明 full-size 插值不应成为 RKNN 的 CPU operator。[RK train_deeplab.py:304](/home/hdzk/YangS01/RK3588-Plaform/workers/trainer/scripts/train_deeplab.py:304) 对已有 full-resolution ONNX，converter 会安全删除唯一终端 4x Resize，并在转换报告中记录原/新 shape 和被改写的节点。[RK graph_optimizer.py:64](/home/hdzk/YangS01/RK3588-Plaform/workers/converter/graph_optimizer.py:64) [RK graph_optimizer.py:141](/home/hdzk/YangS01/RK3588-Plaform/workers/converter/graph_optimizer.py:141) 性能审计还会把非 Input/Output operator 的 CPU 时间识别成 fallback。[RK engine.py:369](/home/hdzk/YangS01/RK3588-Plaform/workers/converter/engine.py:369)

本项目恰好相反：`SegmentationOutput.forward()` 总是把 logits 上采样到输入尺寸，因此导出的 TorchScript/ONNX 包含终端 resize。[本项目 vision_models.py:73](/home/hdzk/YangS01/codex-train-server/worker/forge_worker/vision_models.py:73) 这在 ONNXRuntime 上数值正确，但没有回答该 resize 在 RKNN 上落到 NPU 还是 CPU。RK 项目的测试用一个 CPU `Resize` 占总时间 55.95% 的报告验证 fallback 检测，说明这不是理论风险。[RK converter 测试:397](/home/hdzk/YangS01/RK3588-Plaform/tests/test_converter.py:397)

### 2. INT8 校准如何进入平台流程

RK 项目不是让用户手工给 Toolkit 一个文本文件。API 创建 conversion job 时会校验 calibration dataset 已 ready 且任务类型与模型 profile 相同，并把数据集 checksum 固化到 job spec。[RK service.py:340](/home/hdzk/YangS01/RK3588-Plaform/backend/platform_api/service.py:340) converter worker 下载并校验 archive，解包后按路径排序，最多选 200 张图，生成 Toolkit2 的 dataset list。[RK executor.py:44](/home/hdzk/YangS01/RK3588-Plaform/workers/converter/executor.py:44) [RK calibration.py:10](/home/hdzk/YangS01/RK3588-Plaform/workers/converter/calibration.py:10) 随后 `build(do_quantization=True, dataset=...)`，并上传 `.rknn`、validation report 和 conversion log。[RK engine.py:193](/home/hdzk/YangS01/RK3588-Plaform/workers/converter/engine.py:193) [RK executor.py:90](/home/hdzk/YangS01/RK3588-Plaform/workers/converter/executor.py:90)

### 4. RK 项目自身存在的实现/文档偏差

RK 文档声称 DeepLab RLE 中的 `width/height` 是网络输出 mask 尺寸，消费者再 nearest resize 到源图，以避免板端 CPU resize。[RK runtime 文档:189](/home/hdzk/YangS01/RK3588-Plaform/third_party/nv_video_pipeline/RK3588_RUNTIME.md:189) 但当前 C++ 实现实际对每个类别的 logits 做 bilinear resize 到 `frame.width/frame.height` 后才 argmax，随后序列化这个源分辨率 mask。[RK StructuredInstance:358](/home/hdzk/YangS01/RK3588-Plaform/third_party/nv_video_pipeline/src/rknn_instance/RknnStructuredInstance.cpp:358) [RK DeepLabPostprocess.cpp:55](/home/hdzk/YangS01/RK3588-Plaform/third_party/nv_video_pipeline/src/rknn_instance/DeepLabPostprocess.cpp:55) [RK FrameInferenceResult.cpp:32](/home/hdzk/YangS01/RK3588-Plaform/third_party/nv_video_pipeline/src/objects/FrameInferenceResult.cpp:32)

因此，**按当前代码，RK 项目没有兑现文档所称的低分辨率 RLE 优化**。迁移时应先选择一种权威行为：

- 若追求分割质量，在 logits 上做 bilinear resize 后 argmax，但接受板端 CPU 和大 RLE 成本。
- 若追求吞吐与紧凑结果，在低分辨率直接 argmax/RLE，由消费端 nearest resize，但语义边界与现实现不同。

## 对本项目的迁移含义

若目标是达到 RK 项目的 RK3588 可交付能力，建议按以下依赖顺序推进：

1. **先定模型兼容策略。** 不应把 RK 项目的 `mobilenet_v2_rknn` 当成本项目 `deeplabv3plus-mobilenetv2-rk` 的同名替换。应明确是保留本项目 DeepLabV3+ 拓扑并做 RKNN 适配，还是引入一个新的“Rockchip official-like DeepLabV3 MobileNetV2”变体；后者会改变 checkpoint、精度基线和输出 stride。
2. **建立唯一 deployment contract。** 至少固定输入名、RGB/BGR、NCHW graph layout、runtime NHWC/uint8 接口、mean/std、shape、opset/IR、输出名、输出 layout、stride、labels 和后处理版本。RK 项目的 manifest/validator 可作为参考，但本项目必须使用 ImageNet mean/std，不能照抄 127.5 配置。
3. **把模型内 full-size resize 移出或验证其 NPU placement。** 当前本项目的终端 resize 是最直接的 RKNN 性能风险；应通过图改写或导出专用 deployment forward 解决，并用 `eval_perf` 证实没有非预期 CPU fallback。
4. **新增独立 RK3588 converter worker。** worker 应只在真实 RK3588 节点领取转换任务，显式固定 Toolkit/runtime/driver 版本，支持 FP16 与 INT8、校准数据 checksum、可重复 conversion report。
5. **以实机验证作为发布门禁。** 至少要求 RKNN export、runtime init、一次有效 inference、输出 shape/label 校验；性能 readiness 应与 deployment readiness 分开记录。RK 项目当前发布只强制 `deploymentReady`，并不强制 `performanceReady`，迁移时需要明确是否接受这种策略。[RK engine.py:268](/home/hdzk/YangS01/RK3588-Plaform/workers/converter/engine.py:268) [RK inference_service.py:439](/home/hdzk/YangS01/RK3588-Plaform/backend/platform_api/inference_service.py:439)
6. **最后接入生产 runtime 与平台编排。** 包括 `librknnrt` 输入/输出处理、反量化、后处理、context pool、core mask、release/adapter 映射、节点能力注册、任务激活与健康检查；否则得到的仍只是一个可下载 `.rknn`，不是平台能力。

总体上，RK 项目的优势是部署闭环与可验证契约，本项目的优势是更完整的 DeepLabV3+ 结构和更通用的训练/转换平台。两者最合理的融合方式不是复制 RK 项目的模型实现，而是复用其“manifest -> converter -> device validation -> trusted adapter -> release gate”的体系，同时为本项目现有模型单独完成预处理、输出 stride 和算子 placement 验证。
